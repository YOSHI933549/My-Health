# 食事を調べてアプリに反映する

## 現在の優先経路（Claude Code / Codex共通）

アプリの「AI自動登録（Codex / Claude）」で接続済みの場合は、n8nではなく暗号化受け取り箱を使う。
`codex-devices/<deviceId>.json` の公開鍵を使い、平文の食事JSONを保存せず、次のコマンドで暗号化する。

```bash
node scripts/encrypt-meal.mjs codex-devices/<deviceId>.json < meal.json
```

出力された暗号化エンベロープだけを対応する `codex-inbox/<deviceId>.json` の `entries` に追加する。
差分に平文の食事名・栄養値がないことを確認してコミット・プッシュする。アプリを開くまで反映済みとは
断定しない。接続済みでない場合だけ、以下のn8n経路を互換用の代替として使う。

社長(このリポジトリの持ち主)が食べたものを伝えてきたら、栄養成分を調べて
暗号化受け取り箱に送る。アプリは表示中20秒おきにその箱を見に行くので、
送った時点で「アプリを開けば入る」状態になる。社長の手入力はゼロ。

この仕組み自体の説明は `README.md` の「Codex / Claudeから食事を自動登録」節にある。

## いちばん大事なこと

**栄養面のフィードバック(アドバイス・評価・改善提案)は書かないこと。**
社長から「反映に対してのフィードバックは今後不要」と明示的に言われている。
数値と、反映のしかただけを淡々と伝える。「脂質が多めです」「たんぱく質を足すと」
といった一言も不要。分析はアプリの「分析」タブが担当している。

## 手順

### 1. 何をどれだけ食べたのか確定する

サイズ(並盛/大盛/特盛、M/L)とトッピング(生玉子、チーズ、ドリンクの有無)で
数値は大きく変わる。社長の言葉に含まれていればそれを使う。

言われた名前が現行メニュー名と違うことがある(例:「おろしポン酢牛丼」→ 松屋の
現行メニューは「鬼おろしポン酢牛めし」)。検索で現行名を突き止め、
**どの名前で記録したかを最後の報告に一言添える**。社長が別物を頼んだつもりだと
記録が狂うため。

指定がない要素は、社長を止めずに一般的な構成を仮定して進め、その仮定を報告に書く。
どうしても数値が倍ちがうレベルで割れる場合(セットのドリンク有無など)だけ確認する。

### 2. 公式の栄養成分を調べる

`WebSearch` を使う。検索クエリは「店名 メニュー名 サイズ カロリー たんぱく質 脂質 炭水化物 栄養成分」
のように、欲しい項目名を並べると公式の数値表がヒットしやすい。

**`WebFetch` は多くの場合この環境の通信ポリシーで弾かれる**(matsuyafoods.co.jp,
kalori.jp, 各まとめサイトは実績として EGRESS_BLOCKED)。WebFetch が失敗しても
それは異常ではないので、`WebSearch` の要約から数値を取る方針に切り替えてよい。

### 3. 数値を検算してから信用する

検索結果には別サイズの数値や古い数値が混ざる。実際に「大盛」を調べたとき、
1237kcal(実際は特盛の値)と933kcalが両方返ってきた。そのまま書くと嘘の記録になる。

信用してよいと判断する材料:

- **2回目の検索で同じ数字が出るか。** クエリを変えてもう一度引く。
- **サイズ違いの数値が一列に並ぶか。** 小盛507 / 並盛687 / 大盛933 / 特盛1237 の
  ように、ごはんが増えるぶん炭水化物とカロリーが素直に増えていれば同じ出典の
  一貫した表である可能性が高い。1つだけ飛び抜けている数値は別物を拾っている。
- **PFCからカロリーが逆算できるか。** たんぱく質×4 + 脂質×9 + 炭水化物×4 が
  表示カロリーとおおむね合うか(±10%程度)。大きくずれたら拾い間違い。

複数品を1食としてまとめる場合(牛めし+生玉子など)は、品目ごとの数値を出してから
合計する。合計だけでなく**内訳を memo 欄に残す**と、後から検証できる。

### 4. 受け取り箱に書き込む

`mcp__n8n__add_data_table_rows` を使う。

- `dataTableId`: `kJGO53NKSvLuEWM2`
- `projectId`: `04Oz42Ejb7QWlGu4`

列とその中身:

| 列 | 中身 | 例 |
|---|---|---|
| `date` | JSTの日付 `YYYY-MM-DD` | `2026-09-09` |
| `time` | JSTの時刻 `HH:MM` | `12:00` |
| `type` | `朝食` / `昼食` / `夕食` / `間食` のいずれか | `昼食` |
| `name` | 店名+メニュー名+サイズ | `松屋 鬼おろしポン酢牛めし(並盛)` |
| `calories` | kcal(数値) | `714` |
| `protein` | たんぱく質g(数値) | `18.3` |
| `fat` | 脂質g(数値) | `29.1` |
| `carbs` | 炭水化物g(数値) | `90.8` |
| `memo` | 内訳・食塩相当量・出典 | `食塩相当量4.5g。松屋公式栄養成分より` |

日時は必ず `TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M'` で取る。この環境の既定時刻は
UTCなので、そのまま使うと日付が1日ずれる。社長が「今日の昼」と言えばその日の
昼食として、時刻の指定がなければ食事区分に見合う常識的な時刻(朝食7:30 /
昼食12:00 / 夕食19:00)を入れる。

食事区分の指定がなければ、JSTの現在時刻から素直に決める(〜10時=朝食、
〜15時=昼食、〜21時=夕食、それ以外=間食)。

### 5. 書き込めたことを確認する

`mcp__n8n__get_data_table_rows`(同じ dataTableId / projectId)で読み返し、
今書いた行が入っていることを目で確認してから報告する。

なお **アプリのURL(yoshi933549.github.io)や n8n の webhook URL には、この作業環境から
curl で到達できない**(通信ポリシーで遮断)。到達できなくても壊れているわけではない。
Data Table に行が入っていれば、社長のスマホ側では正常に取り込まれる。
curl の失敗を「反映されていない」と報告しないこと。

## 報告の書き方

短く。数値の表と、社長が何をすればいいかだけ。

```
社長、入れておきました。

## <店名 メニュー名(サイズ)>

| | 数値 |
|---|---|
| カロリー | **714 kcal** |
| たんぱく質 | **18.3 g** |
| 脂質 | **29.1 g** |
| 炭水化物 | **90.8 g** |
| 食塩相当量 | 4.5 g |

アプリを開いて20秒待つか、設定タブの「今すぐ取得」を押すと、
9月9日の昼食に入ります。

出典: <リンク>
```

添えるとよいもの(該当するときだけ):

- メニュー名を読み替えた場合の一言(「現行メニューでは『鬼おろしポン酢牛めし』です」)
- 複数品をまとめた場合の内訳
- 置いた仮定(ドリンクなし、など)

**添えないもの:** 栄養バランスの講評、次の食事の提案、目標に対する達成度。

## 社長への説明のしかた

社長はAIやエンジニアの知識をほとんど持っていない。専門用語(Data Table、webhook、
ポーリング)を出さずに、「受け取り箱に入れておいたので、アプリを開けば入ります」の
ような日常の言葉で書く。表を使うと伝わりやすい。
